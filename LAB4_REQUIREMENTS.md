# Лабораторная работа №4 — BDD E2E тесты аутентификации + 2FA + смена пароля

Цель ЛР: реализовать E2E‑сценарии аутентификации (включая 2FA), плановую смену пароля и восстановление после блокировки **в BDD‑формате**.

Проект — Go, webapp API. Для BDD используется `godog` (Cucumber‑style): сценарии пишутся в `.feature`, шаги реализуются на Go.

---

## Коротко: что добавлено

- 2FA‑флоу для логина:
  - `POST /api/auth/login` → возвращает `challengeId` и отправляет код (2FA)
  - `POST /api/auth/login/verify` → принимает `challengeId + code`, выдаёт `token`
- Плановая смена пароля (с подтверждением 2FA):
  - `POST /api/auth/password/change/request` (Bearer token + old/new password) → `challengeId`
  - `POST /api/auth/password/change/confirm` (`challengeId + code`) → применяет новый пароль
- Восстановление после блокировки:
  - `POST /api/auth/recover/request` → отправляет recovery‑код
  - `POST /api/auth/recover/confirm` → проверяет recovery‑код и задаёт новый пароль
- Лимит попыток ввода 2FA кода + блокировка аккаунта:
  - после `AUTH_MAX_ATTEMPTS` неверных кодов → `429 Too Many Requests` на новые попытки
- BDD E2E тесты:
  - `code/tests/bdd/features/auth.feature`
  - шаги/раннер: `code/tests/bdd/suite_test.go`
- Интеграция в CI/Docker‑раннер:
  - `code/product/run_ci_tests.sh` теперь запускает BDD после обычного e2e.
  - `Makefile` получил `test-bdd-e2e-junit` + интеграцию в `allure-generate`.

## Задание

### 1) Реализовать E2E тесты (BDD) для аутентификации и плановой смены пароля

**Что означает**
- E2E тест — проверяет систему «как пользователь»: через HTTP API, с реальным окружением (webapp + БД), без моков.
- BDD — сценарии поведения в `.feature` (“Given/When/Then”), которые понятны не только разработчикам, но и условному “business”.

**Где реализовано**
- BDD сценарии: `code/tests/bdd/features/auth.feature`
- Реализация шагов + поднятие webapp/БД: `code/tests/bdd/suite_test.go`
- Смена пароля (плановая) проверяется в сценарии *Login with 2FA and planned password change*.

**Как продемонстрировать**
- Локально (BDD прогон):
  - `cd code/tests/bdd`
  - `go run github.com/cucumber/godog/cmd/godog@v0.12.6 --format pretty`
- Через отчёт (Allure через JUnit):
  - `make test-bdd-e2e-junit`
  - затем `make allure-generate` и `make allure-open`

---

### 2) Если аутентификация не была реализована — реализовать в соответствии с BDD

**Что означает**
- Если бы не было `/api/auth/*`, нужно было бы реализовать регистрацию/логин, опираясь на BDD‑сценарии.
- В проекте базовые `register/login` уже были, но не было 2FA/лимитов/восстановления/смены пароля.

**Что сделано по факту**
- Расширен “поведенческий контракт” через BDD сценарии (они задают ожидаемое поведение).
- Реализованы недостающие части аутентификации (2FA, блокировка, восстановление, смена пароля).

## Требования

### (1) Проверяется двухфакторная аутентификация (email/push/мессенджеры)

**Что означает**
- После ввода логина/пароля пользователь должен подтвердить вход вторым фактором.
- Достаточно “email” — в учебном проекте допустима имитация отправки.

**Где реализовано**
- Генерация кода и 2FA‑challenge: `code/apps/webapp/internal/api/auth_flow.go`
- “Отправка” кода:
  - логируется в stdout (как “email”)
  - в тест‑режиме также сохраняется в outbox (чтобы E2E мог получить код)
    - outbox: `code/apps/webapp/internal/api/outbox.go`
    - тестовый endpoint: `GET /api/test/outbox` (только при `WEBAPP_TEST_MODE=1`)

**Как продемонстрировать**
- Запусти BDD тест — он делает login → читает код из outbox → verify.

---

### (2) Ограниченное количество попыток ввода

**Что означает**
- При неверном вводе 2FA‑кода должно быть ограничение (например 3 попытки), иначе возможен brute‑force.

**Где реализовано**
- Счётчик попыток в `challenge.Attempts` и блокировка:
  - `code/apps/webapp/internal/api/auth_flow.go`
  - `AUTH_MAX_ATTEMPTS` (по умолчанию 3)

**Как продемонстрировать**
- BDD сценарий *Limited attempts lock the account* вводит неверный код 3 раза.

---

### (3) Восстановление после блокировки

**Что означает**
- Если пользователь заблокирован (превысил лимит попыток), должен существовать сценарий восстановления доступа.

**Где реализовано**
- `POST /api/auth/recover/request`
- `POST /api/auth/recover/confirm`
- Хранение recovery‑кода и сброс блокировки:
  - `code/apps/webapp/internal/api/auth_flow.go`

**Как продемонстрировать**
- BDD сценарий *Recovery after lockout*:
  - сначала создаёт блокировку,
  - затем делает recovery и логинится заново.

---

### (4) Подготовка теста: техпользователь (проверка/создание/утилизация)

**Что означает**
- Для E2E теста должен быть пользователь, через которого проверяем сценарии.
- Допустимо:
  - проверять наличие заранее созданного техпользователя, или
  - создавать перед тестом и “утилизировать” после.

**Как реализовано**
- В BDD перед каждым сценарием создаётся новый “technical user” с уникальным логином:
  - `code/tests/bdd/suite_test.go` (Before hook + `a technical user is registered`)
- “Утилизация” обеспечивается тем, что поднимается отдельная тестовая БД и удаляется целиком в teardown (E2E среда одноразовая).

---

### (5) Интеграция в CI/CD и отсутствие паролей в явном виде

**Что означает**
- Нельзя хранить “секреты” (пароли) в репозитории/feature‑файлах.
- В CI обычно применяют secrets.

**Как реализовано**
- В BDD сценариях пароли **не прописаны**: пароль берётся из переменной окружения `BDD_TECH_PASSWORD`.
  - Локально: экспортируешь переменную перед запуском.
  - В GitHub Actions: прокидывается из GitHub Secrets.
- Логин техпользователя создаётся на лету (уникальный на сценарий), чтобы сценарии не конфликтовали между собой, даже если в одном сценарии пароль меняется.
- BDD прогон встроен в docker‑раннер:
  - `code/product/run_ci_tests.sh` запускает `godog` и пишет JUnit в `allure-results`.

**Как продемонстрировать (GitHub Secrets)**
- В репозитории GitHub: `Settings → Secrets and variables → Actions → New repository secret`
  - `Name`: `BDD_TECH_PASSWORD`
  - `Value`: пароль для техпользователя (не коммитится в репозиторий).
- Workflow `.github/workflows/lab4.yml` берёт его как `${{ secrets.BDD_TECH_PASSWORD }}` и передаёт в docker-compose.

## Примечание про BDD в контексте проекта

BDD здесь полезен тем, что “заставляет” описать поведение аутентификации как набор ожидаемых сценариев:
- 2FA обязателен после правильного пароля
- лимит попыток и блокировка (security)
- восстановление после блокировки
- плановая смена пароля с подтверждением

Сценарии в `auth.feature` можно воспринимать как “живую спецификацию”: если поведение меняется — сначала меняется сценарий, потом код.
